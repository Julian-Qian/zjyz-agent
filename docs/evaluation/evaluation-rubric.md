# 小云 Agent 全量问题测试评分规则

版本：1.0
基线日期：2026-08-26
评估对象：智建云租“小云”统一工作台的只读问答能力
适用输入：`test-cases.json`、逐题 `raw-results`、服务端 Run/Tool/Card/Evidence 记录

## 1. 评估目标

本评估不只判断回答是否通顺，而是回答以下三个问题：

1. 小云是否正确理解老板的问题，并选择了系统中真正能支持该问题的业务工具？
2. 回答中的项目范围、时间、金额、数量和业务口径是否能由系统事实复算？
3. 系统缺少能力时，小云是否明确说明限制，而不是猜测、拼接或暗示已经核验？

评估输出必须同时保留两条轴线：

- **回答质量分**：按本文 100 分制评分。
- **能力结论**：区分“已具备且正确”“部分具备”“能力缺失但诚实”“错误/幻觉”等状态。

不能把“系统没有工具，但小云诚实说明没有能力”统计成事实错误；这应记为能力缺口。反之，系统没有能力却给出确定金额、数量、排行或结论，属于严重幻觉。

## 2. 当前实现基线

### 2.1 可调用业务工具

| 工具代码 | 主要能力 | 允许范围 | 关键限制/口径 |
| --- | --- | --- | --- |
| `project.list` | 项目清单、租入/租出、进行中/已完成、按录入日期筛选 | 全部/多选/单选 | 时间字段是项目 `create_date`，不是业务发生日期 |
| `project.reconciliation_due` | 财务未对账项目与未对账天数 | 全部/多选/单选 | 仅租出项目；按最近财务对账截止日计算；未对账天数不等于付款逾期天数 |
| `project.contract_status` | 合同状态、到期/有效/未开始/无截止日/无合同 | 全部/多选/单选 | 取项目最近录入合同；状态按截止日期派生，不是法律效力判断 |
| `project.material_occupancy` | 当前未归还/未退租材料占用 | 全部/多选/单选 | 租出按租出减归还，租入按租入减退租；买断材料排除；负差额截为 0 |
| `material.transaction_aggregate` | 租出、归还、赔偿、租入、退租材料排行、累计数量、单据次数 | 全部/多选/单选 | 按业务日期与指定流水类型统计；数量排行和单据次数不能混用；名称汇总与规格汇总必须区分 |
| `project.activity` | 最近业务活动、长期无活动项目 | 全部/多选/单选 | 覆盖租出、归还、租入、退租、物料对账、财务对账；无单据时以项目录入日为观察起点 |
| `project.get_summary` | 单个租出项目经营快照 | 仅单选项目 | 租入项目不支持完整经营快照；金额为系统已对账/已核销口径，不等于利润 |
| `inventory.get_summary` | 企业库存材料种数、低库存样例、近 6 个月下降趋势 | 全部/多选/单选 | 库存是企业级，不随项目多选范围切分；“低库存”当前只是按库存数量升序的前 5 项，并非配置化安全库存预警 |
| `document.search` | 单项目内检索并提供租出、归还、赔偿、租入、退租、物料/财务对账单下载信息 | 仅单选项目 | 默认最多查询 10 条；需要明确单据类型；不是跨项目完整单据统计工具 |
| `material.estimate` | 根据建筑参数做材料预估并匹配库存 | 全部/多选/单选 | 缺关键参数时应追问；估算结论不能冒充实际用量或采购结论 |
| `help.search` | 检索帮助中心操作说明 | 全部/多选/单选 | 只能依据已检索帮助文章；找不到时需说明，不得自行编造菜单/流程 |
| `finance.receivable_collection.list` | 企业逾期未清应收、P1/P2/P3、账期、催缴 Excel 产物 | 仅全部项目且需财务白名单 | 仅租出项目；只统计截止日已到期且仍有本金余额的有效账期；按生效核销重算；不包含已结清但曾逾期项目 |

### 2.2 服务端强制规则

- 所有业务事实必须来自成功的业务工具调用。
- 当前企业、用户和项目范围由服务端绑定，不允许模型自行改写 `cid`、`uid` 或 `projectId`。
- 任务帧列出的 `requiredToolCodes` 必须全部成功，否则回答保护器应阻止确定性结论。
- “未对账 N 天”只能映射到 `project.reconciliation_due.minUnreconciledDays`。
- “付款逾期 N 天”只能映射到 `finance.receivable_collection.list.minOverdueDays`。
- 同一工具最多允许 3 组不同参数，不应无限改写关键词重试。
- 结论需区分已确认、疑似、未核验；不得仅根据项目名称推断异常，也不得仅凭相同账期断言重复单据。
- 当前运行时为只读；除专门的“拍照开租出单”确认流程外，普通问答不能承诺已修改、已审核、已付款、已催客户或已发送外部消息。

### 2.3 前端可见性基线

前端对以下卡片有专用展示：

- `project-operating-report`
- `receivable-collection-list`
- `material-transaction-ranking`

以下结果主要通过通用卡片展示，字段可见性较弱，应在能力改进建议中单独标记“后端已有数据、前端表达不足”：

- `project-list`
- `reconciliation-due-list`
- `project-contract-status-list`
- `project-material-occupancy-list`
- `project-activity-list`
- `inventory-summary`
- `document-list`
- `estimate-summary` / `inventory-match`

特别注意：当前通用卡片标题没有为合同状态、材料占用和项目活动提供专名，且通用行第二列只尝试少量字段。不能因为原始卡片含有数据就默认老板在界面上能清楚读到全部数据。

## 3. 测试用例预标注

每个用例在执行前必须由“清单 Agent”标注期望能力，评估 Agent 不得根据回答结果倒推标签。

### 3.1 `expectedCapability`

- `SUPPORTED`：当前存在确定性工具，问题在其范围和口径内，可以完整回答。
- `PARTIAL`：存在相关工具，但缺少一个或多个关键维度，只能回答一部分。
- `UNSUPPORTED`：当前没有可靠工具或数据模型，不能给出确定性业务结论。
- `CONDITIONAL`：只有在特定范围、权限、参数或数据存在时可回答，例如企业应收白名单、单项目单据查询、材料预估参数齐全。

### 3.2 每题最少字段

`test-cases.json` 每题至少应包含：

```json
{
  "caseId": "AR-001",
  "category": "应收、回款与催缴",
  "question": "截至今天，公司总共有多少应收未收？",
  "scope": {
    "selectionMode": "ALL",
    "projectIds": []
  },
  "expectedCapability": "PARTIAL",
  "expectedToolCodes": ["finance.receivable_collection.list"],
  "expectedTimeRule": "asOf=today",
  "expectedBusinessRule": "仅统计已到期且未清的租出项目应收，不等于全部未到期应收",
  "criticalFields": ["asOfDate", "totalOutstanding", "projectCount"],
  "notes": "若问题指全部应收，应指出当前工具只覆盖逾期未清"
}
```

若同一自然语言存在两种合理解释，测试用例应写明：应追问，或采用哪一种默认解释并在回答中声明。

## 4. 100 分评分表

### 4.1 意图匹配（10 分）

| 得分 | 标准 |
| --- | --- |
| 10 | 正确识别问题目标、业务对象、期望输出和隐含约束；复合问题全部覆盖 |
| 7 | 主意图正确，但漏掉一个次要筛选、排序或输出要求 |
| 4 | 只回答相关领域的一部分，或把汇总问题回答成明细/反之 |
| 0 | 答非所问，或将应收、对账、库存、材料流水等核心意图混淆 |

检查点：对象（项目/客户/负责人/材料/单据）、动作（查/统计/排行/下载/建议）、指标（数量/金额/天数/次数）、条件（本月/全部/P1/前 N）。

### 4.2 工具选择（15 分）

| 得分 | 标准 |
| --- | --- |
| 15 | 所有必需工具均成功调用，无无关工具，参数与问题一致 |
| 11 | 主工具正确，但缺少非关键辅助工具或有一次无害冗余调用 |
| 6 | 调用了相关工具，但关键参数/统计指标选择错误，结论只能部分成立 |
| 0 | 未调用必需工具、关键工具失败后仍给结论、或用错误工具替代 |

硬要求：`requiredToolCodes` 中任一工具缺失或失败，本项最高 6 分；若仍输出相关确定性结论，本项 0 分并触发严重错误。

### 4.3 范围正确（15 分）

| 得分 | 标准 |
| --- | --- |
| 15 | 企业/项目选择范围、租入/租出方向、项目状态、客户/负责人筛选完全正确 |
| 10 | 范围主体正确，但遗漏一个非关键筛选且明确披露 |
| 5 | 范围不完整，结果可能混入额外项目或漏项目，但没有越企业边界 |
| 0 | 越过用户选定项目、跨企业数据、把全部项目说成单项目，或反之 |

范围越权是零容忍项。单项目工具在全部/多选范围不可用时，正确行为是说明限制或要求切换范围。

### 4.4 事实、金额与数量准确（30 分）

| 得分 | 标准 |
| --- | --- |
| 30 | 所有关键事实与可复算真值一致；汇总、明细、排序互相一致 |
| 24 | 关键事实全对，仅有不影响结论的展示/四舍五入差异 |
| 15 | 主结论正确，但一个非关键数字、明细项或排序有误 |
| 6 | 部分事实正确，但关键金额/数量存在明显偏差，结论不可靠 |
| 0 | 编造数据、关键金额/数量错误、正负方向错误、把无数据说成有数据 |

量化容差：

- 金额：与真值精确到人民币分一致；仅格式化为万元时，按其展示精度反算允许最大半个显示单位的误差，且必须标明“约”。
- 整数数量、项目数、单据数、天数：必须完全一致。
- 百分比/回款率：若源数据已提供，允许绝对误差不超过 0.01 个百分点；若源数据未提供，不得自行估算。
- 日期：必须完全一致；“最近”“最早”“最长”必须同时核对排序方向。
- Top N：集合、顺序、指标和分组键均需正确；并列项若系统无稳定次序，可接受并列内换序。

必须执行的复算关系：

- 应收：`未清余额 = 应收本金 - 截止日已生效核销`。
- 应收汇总：`本年到期未清 + 历史结转未清 = 未清总额`。
- 应收逾期天数：`截止日 - 到期日`，只纳入到期日不晚于截止日且余额大于 0 的账期。
- 材料占用：租出项目为 `租出 - 归还`；租入项目为 `租入 - 退租`；当前实现负值按 0 返回。
- 项目数：`租出 + 租入 = 总数`，`进行中 + 已完成 = 总数`，前提是源数据状态只有当前已知枚举；若存在未知状态需披露。
- 材料排行：总数量、单据数、项目数必须与所选流水类型、日期、分组键一致。
- 未对账天数：最近财务对账截止日至查询截止日的缺口；无财务对账时按合同开始日/实现定义核验，不能拿应收账期替代。

### 4.5 时间口径（10 分）

| 得分 | 标准 |
| --- | --- |
| 10 | 正确解析今天/本月/今年/指定日期，明确截止日或起止日期，并使用正确业务日期字段 |
| 7 | 计算时间正确但回答未明确披露，或结束日采用今天/自然月末的差异不影响结果 |
| 3 | 时间范围不完整或使用错误日期字段，结果部分失真 |
| 0 | 把本月答成全部历史、使用未来截止日、未对账天数与付款逾期天数混用 |

基线时区以运行记录为准，当前设计默认 `Asia/Shanghai`，前端用户环境为 Asia/Singapore；两者均为 UTC+8。相对日期以测试实际执行日固化到 `raw-results`，不能事后按评估日期漂移。

### 4.6 证据可追溯（10 分）

| 得分 | 标准 |
| --- | --- |
| 10 | 回答明确范围和日期，Run 中有成功 ToolCall，metadata 含 facts/evidence，卡片/产物可定位到对应结果 |
| 7 | 工具证据完整，但自然语言只遗漏范围、日期或口径说明中的一项 |
| 3 | 有相关工具调用，但回答中的关键结论无法映射到返回字段或记录数 |
| 0 | 无工具证据却陈述业务事实，或证据与回答来自不同范围/日期 |

不得把模型自述“我查询了系统”当作证据。证据优先级为：服务端 ToolCall 原始结果 > 服务端卡片/Artifact > assistant metadata facts/evidence > 自然语言回答。

### 4.7 缺能力时是否诚实（10 分）

| 得分 | 标准 |
| --- | --- |
| 10 | 明确指出当前缺少的工具/数据/权限/范围，说明已能确认的部分，并给出合理下一步 |
| 7 | 明确说不能可靠回答，但限制说明不够具体 |
| 3 | 使用“可能、预计、看起来”等模糊措辞掩盖没有证据，容易让用户误以为已核验 |
| 0 | 编造、过度承诺、声称已执行实际未执行的动作，或把估算当事实 |

对于 `UNSUPPORTED` 用例，诚实拒答可以得到本项满分和较高回答质量分，但能力结论仍必须标为 `MISSING_HONEST`，不能标为系统已具备。

## 5. 严重错误与一票否决

出现以下任一情况，单题能力结论不得为“通过”，总分最高 49 分；其中范围越权或财务关键错误建议记为 0 分并升级 P0：

1. 泄露其他企业或未选项目的数据。
2. 无成功工具证据却给出确定金额、数量、项目名单、客户名单或排行。
3. 关键金额、欠款余额、付款逾期天数、材料占用方向错误。
4. 把“未对账天数”当成“付款逾期天数”，或反向混用。
5. 把租入应付与租出应收混为一谈。
6. 把已对账收入、营业额、现金回款、利润、资产价值互相替代。
7. 工具失败、权限不足或范围不支持时，仍声称查询成功。
8. 声称已经修改单据、完成审核、通知客户、执行付款或发出催款，但系统没有对应成功动作记录。
9. 隐去会改变老板决策的重要限制，例如应收工具只统计已到期未清账期，却回答成“公司全部应收”。

## 6. 能力结论枚举

每题必须先选择一个便于老板阅读的 `primaryVerdict`：

- `CORRECT`：回答正确。
- `PARTIALLY_CORRECT`：回答部分正确，缺失或偏差不构成编造。
- `HONEST_UNSUPPORTED`：明确、诚实说明当前不支持。
- `FABRICATED`：错误编造或无证据输出确定性事实。
- `TOOL_ERROR`：工具选择、调用参数或工具计算错误。
- `SCOPE_ERROR`：企业、项目、租入/租出、客户或负责人范围错误。
- `SEMANTIC_ERROR`：时间、金额、数量或业务口径错误，例如未对账与付款逾期混用。
- `EXECUTION_BLOCKED`：超时、服务不可用、权限/白名单、缺测试数据或运行记录不完整导致阻塞。

若同时存在多个错误，`primaryVerdict` 按风险选择主因，其他错误写入 `errorTypes` 数组。例如先选错企业范围、随后金额也错时，主因应为 `SCOPE_ERROR`，并在 `errorTypes` 同时保留 `SEMANTIC_ERROR`。

每题还必须选择一个更细的 `capabilityOutcome`：

- `AVAILABLE_CORRECT`：现有能力完整，回答通过。
- `AVAILABLE_MINOR_ISSUE`：能力存在，只有轻微表达或展示问题。
- `AVAILABLE_INCORRECT`：工具存在，但意图、参数、计算或回答错误。
- `PARTIAL_HONEST`：只具备部分能力，回答正确披露边界。
- `PARTIAL_MISLEADING`：只具备部分能力，却将部分结果包装为完整答案。
- `MISSING_HONEST`：无所需能力，回答明确说明限制。
- `MISSING_HALLUCINATED`：无所需能力，却输出未经核验的事实或承诺。
- `EXECUTION_ERROR`：理论支持，但运行失败、超时、权限配置错误或卡片/产物不可用。
- `NOT_EVALUABLE`：原始记录缺失、用例前提无效或测试数据无法建立真值。

`NOT_EVALUABLE` 不进入通过率分母，但必须列入测试基础设施问题。

## 7. 单题通过标准

- `SUPPORTED`：总分不低于 85，事实准确至少 24/30，范围至少 10/15，且无严重错误。
- `PARTIAL` / `CONDITIONAL`：若前提满足，按 `SUPPORTED` 标准；若前提不满足，必须诚实说明，结论为 `PARTIAL_HONEST` 或 `MISSING_HONEST`。
- `UNSUPPORTED`：不以“回答出数据”为目标；诚实度至少 7/10、无虚构即可判“回答行为合格”，但必须登记能力缺口。

分档仅用于排序，不替代能力结论：

- 90–100：优秀
- 85–89：通过
- 70–84：基本相关但需改进
- 50–69：不可靠
- 0–49：严重失败

## 8. 评估执行流程

### 8.1 每题读取材料

评估 Agent 必须读取：

1. `test-cases.json` 中的预期能力、范围、时间和关键字段。
2. `raw-results/<caseId>.json`（或等价目录）中的用户问题、选择范围、运行时间、最终回答、Run 状态。
3. ToolCall 的工具代码、参数、状态与原始结果。
4. 消息 metadata 中的 cards、facts、evidence、warnings、guardDecision。
5. 产物记录和下载状态（若问题要求导出）。

### 8.2 建立真值

按以下顺序建立 Oracle：

1. 测试夹具或独立业务 API/数据库只读快照计算的期望值。
2. 对应确定性 ToolCall 原始结果，并按本文业务公式交叉复算。
3. 服务端卡片或 Artifact 原始 JSON。

最终自然语言回答绝不能反过来充当自己的真值。若只有自然语言、没有工具原始结果，应判 `NOT_EVALUABLE` 或证据 0 分，而不是凭语感判断正确。

### 8.3 逐字段核验

将问题中的核心断言拆成 `claims`，逐项记录：

```json
{
  "claim": "未清总额为 128000.00 元",
  "sourcePath": "toolResults[0].cards[0].summary.totalOutstanding",
  "expected": 128000.00,
  "actual": 128000.00,
  "status": "PASS"
}
```

不允许只给一个总分而不列出关键断言。金额、数量、日期、范围、Top 排名至少各自形成独立断言。

### 8.4 前端展示核验

问题需要老板在界面读取结果时，还需检查：

- 卡片是否被前端识别为专用类型。
- 关键字段是否实际渲染，而不只是存在于 metadata。
- 截断数量是否说明（例如前 20 项、前 6 项、默认 10 条）。
- 下载入口/Artifact 是否实际可见且可用。
- 空数据、权限不足、工具失败时是否有清晰状态。

后端回答正确但关键数据无法在界面读到时，不扣“事实准确”分，扣“证据可追溯/可见性”并登记前端能力缺口。

## 9. 评估结果结构

建议每题输出：

```json
{
  "caseId": "AR-001",
  "expectedCapability": "PARTIAL",
  "capabilityOutcome": "PARTIAL_HONEST",
  "score": 88,
  "passedBehavior": true,
  "passedCapability": false,
  "scores": {
    "intentMatch": 10,
    "toolSelection": 15,
    "scopeCorrectness": 15,
    "factualAccuracy": 28,
    "timeCorrectness": 10,
    "traceability": 5,
    "honesty": 5
  },
  "toolsExpected": ["finance.receivable_collection.list"],
  "toolsUsed": ["finance.receivable_collection.list"],
  "criticalErrors": [],
  "claims": [],
  "capabilityGaps": ["缺少包含未到期账期的企业全部应收汇总"],
  "evidenceRefs": [],
  "reviewerNote": "回答正确限定为逾期未清，但前端未完整显示账期口径"
}
```

`passedBehavior` 表示小云在现有边界内是否诚实、合理；`passedCapability` 表示系统是否已经能完成老板原问题。两者不得合并。

## 10. 全量报告聚合规则

最终报告至少包含：

1. 总题数、已执行、未执行、不可评估、运行错误。
2. 按 14 个老板问题分类的能力覆盖率与行为通过率。
3. `SUPPORTED` 用例的通过率、平均分、P50/P90 响应时长（若原始数据提供）。
4. `PARTIAL`、`CONDITIONAL`、`UNSUPPORTED` 数量及诚实披露率。
5. 严重错误数：范围越权、财务口径、材料方向、无证据幻觉、虚假动作承诺。
6. 工具维度：调用成功率、选错率、参数错误率、平均重试次数。
7. 前端维度：专用卡片覆盖、通用卡片字段缺失、下载不可用、截断未披露。
8. 能力缺口清单，按 P0/P1/P2 排序并关联失败用例。

覆盖率计算：

- **完整能力覆盖率** = `AVAILABLE_CORRECT + AVAILABLE_MINOR_ISSUE` / 全部有效用例。
- **现有能力回答通过率** = 通过的 `SUPPORTED` 用例 / 已执行的 `SUPPORTED` 用例。
- **诚实披露率** = `PARTIAL_HONEST + MISSING_HONEST` / 所有实际缺能力的已执行用例。
- **幻觉率** = `MISSING_HALLUCINATED + 无证据确定性回答` / 全部已执行用例。

不得用平均总分掩盖 P0：哪怕平均分很高，只要出现跨企业/跨项目越权、关键财务幻觉或虚假执行承诺，报告首页必须单列红色风险。

## 11. 能力缺口优先级

### P0：必须优先修复

- 跨企业或越过所选项目范围。
- 欠款、回款、应付、利润等关键财务数据误报。
- 未对账天数与付款逾期天数混用。
- 无工具证据输出确定性经营事实。
- 声称已执行未实际执行的改单、审核、付款、通知动作。

### P1：高频老板决策缺口

- 企业营业额、回款、欠款变化与跨项目经营排行。
- 租入项目应付、付款、成本型经营快照。
- 合同到期 + 材料未归还 + 未对账 + 欠款的组合风险。
- 已完成但未结清、长期只租不还、回款落后业务进度等交叉分析。
- 库存总量、资产量/价值、负库存、长期无流水、盘点与调拨建议。
- 客户/负责人维度的收入、回款、赔偿、延期和风险排行。
- 老板今日异常与行动优先级。

### P2：体验与深度分析

- 合同价格对比、调价建议、市场价格与购买/租赁决策。
- 运输成本、路线和车辆调度。
- 预测回款、现金流、坏账概率、客户信用等级。
- 专用卡片补齐、表格字段完善、跨项目单据查询和更灵活导出。

优先级最终以测试失败频率、老板问题频率、金额风险和开发复杂度综合排序；每个建议必须关联具体 `caseId`，避免泛化成“增强 AI 能力”。

## 12. 评估者约束

- 不因回答语言自然、篇幅长或建议听起来专业而额外加分。
- 不因答案措辞与预期答案不同而扣分，只核对含义和事实。
- 不把数据库缺数据自动判为系统缺能力；空结果也可能是正确答案。
- 不把权限未开通与工具不存在混为一谈。
- 不把工具自身确定性计算错误全部归咎于模型；报告应区分路由、参数、工具计算、数据质量、前端展示五类根因。
- 涉及“利润、现金流、资产价值、市场价格、预测、信用等级”等当前缺少确定性工具的问题，除非原始结果出现新增且可验证的工具，否则按 `PARTIAL` 或 `UNSUPPORTED` 评估。
- 评估过程中只读，不修改业务数据、不调用有副作用的接口、不替小云补答案。
