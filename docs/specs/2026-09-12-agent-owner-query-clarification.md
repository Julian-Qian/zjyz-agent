# 负责人项目查询与无效澄清修复

用户要求继续修复“目前小何在负责哪些项目”被询问“系统是否支持按负责人筛选项目”，以及回复后旧确认卡仍显示的问题。

## 实现

- 理解器明确区分业务缺失条件与系统能力：工具是否存在应由能力清单判断，不能让用户确认。删除此类无效 missingInputs，保留具体人员身份等真实缺失条件。
- 对完整、严格匹配的“某人负责哪些项目”查询做服务端校验；即使模型返回 UNKNOWN，也恢复为只读项目查询。“他”“我”等代词不按登记姓名执行。
- 默认“负责”对应我方负责人；新增 `managerName`、`partnerName` 独立工具参数，分别限定我方与对方负责人。按登记姓名包含匹配，不推测昵称全名，不混搜项目名或客户名。
- “目前”表示当前登记的负责人关系，不自动按录入日期、项目状态或租入/租出方向过滤。冻结项目范围和企业隔离沿用现有实现。
- 回复旧的系统能力澄清时，只有绑定 interactionId、对应能力问题且上一任务是完整负责人查询，才恢复原始目标；“支持”不提供额外权限。
- 前端忽略其他任务的旧事件，过滤已回答/已过期/已取消的确认卡及终态任务的确认卡，支持持久化的 promptText。真实待补充问题继续显示。

## 验证

- 后端隔离副本 Maven 编译及 29 项定向测试通过，写回后校验源码哈希一致。
- 前端任务展示和交互状态共 30 项测试通过。
- 前端生产构建通过；输出已有的 Hook 依赖、未使用变量、Browserslist 数据及包体积警告，本轮修改文件未报告 ESLint 警告。
- 前后端 `git diff --check` 通过。
- 未改 HTTP 路径或数据库结构；未部署、未查询生产负责人数据、未进行真实模型或浏览器端到端验收。

姓名包含匹配可能返回多个负责人同名或部分匹配结果，回答会明确包含匹配口径；无匹配时提示补充系统登记姓名。人员实体与昵称映射不在本轮范围内。
